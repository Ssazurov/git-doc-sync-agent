Обновляет локальный файл состояний sync\_state.json, переводя статус найденных разделов в "Stale" (устарел). 3\. **Агент-Редактор (Drafting Assistant Agent)** \* **Роль:** Технический писатель-генератор. \* **Инструменты:** LLM (локальная Qwen 2.5 через Ollama). \* **Задача:** Когда техписатель запрашивает авто-разметку, этот агент анализирует изменения в коде, читает XML-раздел и генерирует точные ИИ-комментарии (Todo) или черновик нового текста для вставки в XML. 4\. **Агент-Координатор (GitHub & Git-PR Agent)** \* **Роль:** DevOps-ассистент. \* **Инструменты:** PyGithub (для работы с API GitHub). \* **Задача:** По команде из UI создает новую ветку в репозитории, применяет изменения в XML/MD (вставляет комментарии/черновики), делает коммит, пушит ветку, создает **Pull Request** или заводит структурированную задачу в **GitHub Issues**. \--- \#\#\# 🗃️ Схема хранения данных и предотвращения конфликтов Чтобы работа ИИ не затирала локальные правки техписателя и не вызывала merge-конфликты, мы разделим уровни хранения: 1\. **Файл состояний (sync\_state.json)**: Агент ведет учет связей и статусов локально. Это база данных нашего дашборда. 2\. **Сайт документации (Streamlit)**: Рендерит XML/DocBook-документы прямо в браузере. Если раздел в sync\_state.json имеет статус "Stale", Streamlit подсвечивает этот блок красной рамкой с плашкой: *«Внимание: Метод login\_user() изменен в коммите \#a1b2c3. Требуется актуализация»*. 3\. **Безопасный Git-Flow**: ИИ никогда не пишет в main напрямую. Если техписатель нажимает кнопку *"Сгенерировать Todo в ветку"*, создается ветка docs-sync/patch-\[commit\_hash\]. Писатель делает git pull, забирает ветку, видит комментарии ИИ прямо в своей IDE, дорабатывает файл и мержит его. \--- \#\#\# 📚 Тестовые документы (Self-Monitoring) Проект будет **мониторить сам себя**\!
