🕵️‍♂️ Карта агентов (Команда Sync-Agents)
Для реализации этой логики нам понадобятся 4 специализированных агента, оркестрируемых графом состояний (StateGraph) в LangGraph:
Агент-Детектив (AST-Detective Agent)
Роль: Системный архивариус Git.
Инструменты: GitPython (для работы с репозиторием) + встроенная библиотека ast (для парсинга синтаксического дерева Python).
Задача: Сравнивает текущий коммит с предыдущим (или по расписанию), строит AST-дерево измененных файлов и вычленяет точные имена добавленных, удаленных или измененных методов (например, auth.py::login_user).
Агент-Навигатор (XML-Navigator Agent)
Роль: Эксперт по структуре документации.
Инструменты: lxml (быстрый парсинг XML/DocBook через XPath) или Markdown парсеры.
Задача: Сканирует файлы документации (.xml, .md), ищет теги со связями (например, <section code_ref="auth.py::login_user"> или <!-- code_ref: auth.py::login_user --> для Markdown). Обновляет локальный файл состояний sync_state.json, переводя статус найденных разделов в "Stale" (устарел).
Агент-Редактор (Drafting Assistant Agent)
Роль: Технический писатель-генератор.
Инструменты: LLM (локальная Qwen 2.5 через Ollama).
Задача: Когда техписатель запрашивает авто-разметку, этот агент анализирует изменения в коде, читает XML-раздел и генерирует точные ИИ-комментарии (Todo) или черновик нового текста для вставки в XML.
Агент-Координатор (GitHub & Git-PR Agent)
Роль: DevOps-ассистент.
Инструменты: PyGithub (для работы с API GitHub).
Задача: По команде из UI создает новую ветку в репозитории, применяет изменения в XML/MD (вставляет комментарии/черновики), делает коммит, пушит ветку, создает Pull Request или заводит структурированную задачу в GitHub Issues.
🗃️ Схема хранения данных и предотвращения конфликтов
Чтобы работа ИИ не затирала локальные правки техписателя и не вызывала merge-конфликты, мы разделим уровни хранения:
Файл состояний (sync_state.json): Агент ведет учет связей и статусов локально. Это база данных нашего дашборда.
Сайт документации (Streamlit): Рендерит XML/DocBook-документы прямо в браузере. Если раздел в sync_state.json имеет статус "Stale", Streamlit подсвечивает этот блок красной рамкой с плашкой: «Внимание: Метод login_user() изменен в коммите #a1b2c3. Требуется актуализация».
Безопасный Git-Flow: ИИ никогда не пишет в main напрямую. Если техписатель нажимает кнопку "Сгенерировать Todo в ветку", создается ветка docs-sync/patch-[commit_hash]. Писатель делает git pull, забирает ветку, видит комментарии ИИ прямо в своей IDE, дорабатывает файл и мержит его.
📚 Тестовые документы (Self-Monitoring)
Проект будет мониторить сам себя! Для тестирования мы создадим:
docs/installation_guide.xml (Руководство по установке продукта).
docs/admin_guide.xml (Руководство администратора).
Оба документа напишем на DocBook XML (с возможностью легкой конвертации в Markdown).
Мы пропишем в них теги связей с методами нашего собственного API (например, методы запуска сервера, инициализации БД и т.д.). Когда мы будем менять код нашего ассистента — система будет регистрировать изменения и подсвечивать разделы в собственной документации!
